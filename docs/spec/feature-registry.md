# 开发对齐

## 一、对齐规则

研究侧和开发侧靠同一套功能编号对齐。本 tab 是功能规格的唯一来源；仓库里放它的副本；Claude Code 只按编号核对和改动。

1. **编号**：每个功能一个编号（C01–C22）。代码注释（`// SPEC:C05`）、提交信息、测试名都引用它；研究侧的材料表和修订对照表也引用同一编号。
2. **仓库副本**：把本 tab 导出为 `docs/spec/feature-registry.md` 放进仓库。Claude Code 只读这份副本，不自己改规格。
3. **核对结果**：Claude Code 把结果写成 `docs/spec/audit-YYYYMMDD.md`，逐个编号填锚点位置、是否一致、证据。你把它贴回第四节，我更新第二节的状态栏。
4. **改动流程**：研究侧要改功能，先改本 tab 那一行（写明改了什么、为什么），再重新导出到仓库，最后让 Claude Code 按编号实现。开发中发现代码与规格不符，先在本 tab 记下，不直接改代码。
5. **两组对等**：除登记表写明的组间差异外，两组的界面、推送、问卷、安全流程必须一致。每一项都要看两组。
6. **冻结**：第一位正式参与者入组前，给 Phase B 构建打 tag（如 `phaseB-v1.0`），把提交号写进第四节。之后的任何改动都记入偏离日志，并判断是否要报 HREC。

## 三、给 Claude Code 的核对 prompt

用法：(1) 把本 tab 导出的 markdown 放到仓库的 `docs/spec/feature-registry.md`；(2) 在仓库根目录打开 Claude Code，贴下面这段；(3) 跑完后把 audit 文件贴回第四节。

```text
你是这个仓库（陪住 / With You，Flutter + Firebase）的资深工程师。本次任务只读代码，不改代码，不提交。

输入：docs/spec/feature-registry.md。它是研究侧的功能登记表，编号 C01–C22。每个编号写了“Hybrid 组应有”“Rule-based 组应有”和“要核对的锚点”。登记表是规格的唯一来源，不要改它。

对每个编号：
1. 找到“要核对的锚点”里列的每一处：文件路径（到函数名或行号）、Firestore 集合和字段、开关名和默认值、prompt 或内容文件。
2. 判断实际行为与登记表是否一致，结论只用四种：一致 / 不一致 / 缺失 / 无法判断。Hybrid 和 Rule-based 两组都要看。
3. 给出证据：代码位置，或你运行的命令及输出。找不到就写“未在代码中找到”，不要猜；推断的内容标“（推断）”。
4. 登记表写“待确认”或“待定”的项，只报告现状，不判断对错。

另外两件事：
- 两组在登记表之外如果还有任何差别（界面、导航、推送、问卷、安全流程），单独列出。
- 如果仓库有测试，跑一遍，报告与登记表编号相关的通过和失败。

输出写到 docs/spec/audit-YYYYMMDD.md：
- 开头摘要，不超过 10 行：不一致、缺失、无法判断的编号清单。
- 一张表：编号 | 锚点位置 | 结论 | 证据 | 备注。
- “登记表之外的组间差异”一节。
- “我最不确定的 3 处”一节。
写完告诉我文件位置。

第二步（等我确认核对结果后再做）：在每个锚点处加注释 `// SPEC:Cxx`，单独一个提交，提交信息写“spec anchors C01–C22”。
```
