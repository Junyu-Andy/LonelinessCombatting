# 需求说明和建议：没法更新 App 的参与者（旧版本手机）

> 2026-10-20 开发窗口写，给产品窗口审核。产品定稿后，按定的方案出开发交接。**这一份只是需求和建议，还没有写代码。**

## 结论

- **问题**：有的参与者没法更新到 10/21 的新版本。比如那部 iPhone 7 Plus 用不了 TestFlight；有的人自己装不了 APK；也没法每次都约他们来面访。旧版本 App 会一直留在他们手机上。
- **真正会出错的只有一处：每周问卷。** `weeklyReminderV2Enabled` 打开以后，服务器按新时间开关问卷、发推送，旧 App 还按旧时间显示。老人会收到「问卷开放了」，打开 App 却显示「还没开放」；或者 App 里还能填，服务器已经关了，记成缺失。
- **建议**：给这些人加一个「旧版本」标记，由研究员手动设置。服务器看到这个标记，就对这个人继续用旧的每周问卷规则，和他手机上的旧 App 一致。其他人照常用新规则。
- **不急在 10/21。** 问卷开关只在有人到了第 6–9 天（第 1 周预告到关闭）才起作用。只要在**最早一位参与者到第 6 天之前**做完就行，具体日期请产品核对。在那之前 `weeklyReminderV2Enabled` 先不开，其他开关照计划开。
- 界面上的新功能（对话式 check-in、首页两页、心情一行等）**旧版本永远没有**，服务器补不了。这些人要记一笔方案偏离（protocol deviation）。

## 一、哪些功能在旧版本上会出问题

| 开关 | 谁决定行为 | 旧版本手机上会怎样 | 要不要处理 |
|---|---|---|---|
| `weeklyReminderV2Enabled` 每周问卷整日窗口、10:00 推送、给 Junyu 的未完成电邮 | **服务器和 App 都参与，而且必须一致** | 推送时间和 App 显示的开放时间对不上；App 里显示还能填，服务器已经关了 | **要处理**（第二节） |
| `checkInChatV2Enabled` 08:30 P1、19:00 P2 | 推送由服务器决定；小欣页的样子由 App 决定 | 推送照常收到。旧表单做的 check-in，服务器也算「做过」（`check_in_responses` 里没有 `flow` 的旧行算完成），不会做完了还被提醒。小欣页还是旧表单 | 推送不用处理；界面算方案偏离 |
| `homeLayoutV2Enabled`、`moodRowV2Enabled`、`reminiscenceV2Enabled`、`actionPlanSimplifiedEnabled`、`htmlReadersEnabled` 等 | 只有 App | 旧版本不认识这些开关，一直是旧界面 | 补不了，算方案偏离 |
| 小欣、阿珍阿伯、通通的 LLM 提示词 | 服务器 | 旧 App 发旧的提示词名（例如 `siu_yan_v1`），服务器现在还认，照常回复 | 不用处理；开发只做兼容核对（第四节） |
| 安全检测（`lib/core/safety/`） | **只在 App 里** | 旧版本用的是旧的词表和规则 | **要核对**（第四节）：旧版本的安全检测是否可以接受 |

## 二、建议的做法：按人标记「旧版本」

### 怎么标记

- 每个参与者的用户资料里加一个只有服务器能写的字段，例如 `users/{uid}.legacyClient`，值是 `true`，同时记下设置日期和原因。
- 研究员用一个工具设置，和现在发角色的 `provision_researcher.js` 一样，用研究编号指定人：

  ```bash
  NODE_PATH=functions/node_modules node tool/set_legacy_client.js --participant=<研究编号> --on --reason="iPhone 7 Plus，iOS 15，不能装 TestFlight"
  ```

  另有 `--off`（这个人后来更新了）和 `--list`（列出所有标了旧版本的人）。每次设置和取消都要留记录。
- 不需要知道这个人在哪一组。工具和记录里都不出现组别。

### 标了以后服务器怎么做

| 事项 | 标了「旧版本」的人 | 其他人 |
|---|---|---|
| 第 1–3 周问卷的开放和关闭 | 旧规则：第 7 天 20:00 开，开 72 小时 | 新规则：第 7 天 00:00 到第 9 天 23:59 |
| 问卷推送 | 旧规则：开放时一条，24 小时后还没答再一条，都在 20:00 | 新规则：10:00 预告、开放、提醒 |
| 第 4 周 | 旧规则 | 新规则（到 W4 面访录入那天） |
| 缺失和「窗口外」的标记 | 按他自己那套窗口算 | 按新窗口算 |
| 给 Junyu 的未完成名单电邮 | **待产品定**：建议照样列进名单，按他自己的窗口算；名单里注明「旧版本」 | 照常 |
| 08:30 P1、19:00 P2 | 和其他人一样 | 照常 |

### 为什么建议手动标记，不让服务器自动判断版本

- 服务器现在能看到 App 上报的版本号，但**不可靠**：GitHub 打的安卓包版本号一直是 `1.0.0+3`，新旧版本分不出来。
- 需要标记的人很少，研究员都认识。手动标记清楚，也方便核查。
- 以后可以另外加一项：App 每次启动时上报一个可靠的构建号（例如打包日期加提交号）。到时候就能自动发现「谁还在用旧版本」，但是否标记仍然由研究员决定。这一项不急，可以放进待办。

## 三、其他建议

1. **安卓以后更新不用卸载。** 现在 GitHub Actions 每次打包都用一把新的随机签名钥匙，所以装新版本必须先卸载、再重新登录，老人自己做不到。建议给 GitHub Actions 配一把固定的测试签名钥匙，放在仓库的 Secret 里，以后的 APK 都能直接覆盖安装。手机上已经装着的旧包还是要卸载一次，但以后就不用了。
2. **记方案偏离。** 每位标了旧版本的人，记下研究编号、手机型号、系统版本、App 版本和 build 号（在「自己 → 關於」里看）、开始日期、缺了哪些功能。分析时可以做一个排除这些人的敏感性分析。
3. **能远程帮他更新就更新。** 例如家人或社工到场时，用视频通话指导安装一次。更新以后取消标记（`--off`），从那天起走新规则，并在 changelog 里写明日期。

## 四、要开发核对的事

1. **这些旧版本到底是哪一版。** 产品给出每个人「關於」页显示的版本和 build 号，开发查出对应的提交，确认这一版和明天的服务器配合不会出错：能登录、聊天、做 check-in、交问卷，安全流程正常。
2. **旧版本的安全检测。** 对比旧版本和现在的 `lib/core/safety/`，说明差在哪里，是否可以接受。如果旧版本有已知漏检，要产品和 Junyu 决定怎么处理，例如加强人工跟进。
3. **规则组旧版本有没有模板回应。** 10/15 以前的部分包打包时没带 `RULE_TEMPLATE_REPLIES`（见 `w0-install-script.md` 2.1、2.3）。如果某位旧版本用户在规则组，那个包可能没有模板回应。开发只查「这个包带没带这个参数」，不需要知道组别。
4. **LLM 提示词兼容。** 旧 App 发的提示词名，服务器现在都还认（`functions/prompt_registry.js`）。开发确认以后改提示词时，不能删旧的名字。

## 五、要产品定的事

1. 用不用「按人标记旧版本」这个方案。另外两种做法：
   - **全部人都不开 `weeklyReminderV2Enabled`**，一直用旧规则：不用写代码，但 1020e 定的整日窗口、10:00 推送和未完成名单电邮就全都没有了。
   - **照开，对旧版本的人不处理**：靠 Junyu 打电话提醒，接受可能多出来的缺失数据。
2. 标了旧版本的人，要不要进给 Junyu 的未完成名单电邮（建议进，并注明「旧版本」）。
3. 现在有哪几位是旧版本：研究编号、手机、系统版本、App 版本和 build 号。不要写组别。
4. 最早一位参与者第 6 天是哪天，也就是这一项的截止日期。在那之前 `weeklyReminderV2Enabled` 先不开。
5. 要不要做第三节第 1 条（安卓固定签名钥匙）。

## 六、如果采用，开发要改的地方（估计）

- 服务器：`functions/weekly_schedule.js`、`functions/weekly_email.js` 按 `legacyClient` 分两套规则；`firestore.rules` 规定这个字段只有服务器能写；新工具 `tool/set_legacy_client.js` 和它的测试；模拟器测试覆盖两种人在同一天收到的推送和窗口。
- App：不用改，旧版本也没法改。新版本 App 不读这个字段。
- 文档：一份决策记录、`STUDY_CHANGELOG`（影响的人和生效日期）、`architecture`、`history`。
- 工作量：大约一个 PR，半天到一天，加上测试。
