# 0069：研究用原文存下老人的每一句和陪伴者显示的每一个气泡，两组相同（部分取代 0063）

- 日期：2026-10-20
- 状态：提议中（Junyu 10/20，decisions-log 第 65、80、99/100 条要求；随 10/21 冻结构建上线，要同时部署 `firestore.rules`）
- 影响范围：phase_b、pilot（含 RCT-）× 两组；测试员也写；只在开关 `researchTranscriptEnabled` 开着时
- 相关代码：分支 `claude/zealous-fermat-8rgqtg-transcript2`（并入 #151）；`lib/core/session/chat_session_recorder.dart`（`TranscriptRow`、`TurnRecord.shownReply`、`ChatSessionRecorder.transcriptCompanion` / `transcriptButton`）、各聊天页、`lib/features/crisis/presentation/widgets/crisis_chat_message.dart`、`lib/app/app.dart`、`firestore.rules`、`tool/check_blinded_export.js`

## 背景

0063 的原文只在「老人发一句、陪伴者回一句」时写一行，回复只存模型或模板那一句。逐页查下来，老人看得到却没存的有：开场白；check-in 的固定问题（Q0–Q6）和按钮回答；回复后面接着问的下一题；回忆 v2 的开场三句、每一题和收尾句；安全句和急性后的安全消息；模型失败时显示的后备句（存成了模型的空字）。回复被安全扫描拦下时，还存了老人没看到的模型原字。操纵检验要读整段对话，这样读不全。

## 决定

1. **同一个集合、同一个开关。** 仍写 `users/{uid}/chat_transcripts`，仍只在 `researchTranscriptEnabled` 开着时写。不加新开关。新行 `schemaVersion: 2`，多两个字段：`role`（`elder` 老人／`companion` 陪伴者）、`userInput`（`text` 打字／`voice` 讲话／`button` 按钮）。
2. **老人的每一句一行。** 按的按钮也算一句，存按钮上的字（`userInput: button`）。`replyText` 存这一句之后、老人下一句之前陪伴者显示的**全部气泡**，按顺序，中间空一行。例：老人答完 Q3b，这一行存「回应一」和「Q4」。发出去记成一轮的，行号和 `turns` 相同；只按按钮、没有记一轮的，行号另起。
3. **老人开口前陪伴者先说的，存成「陪伴者」一行**（`role: companion`，老人的字段都是空）：开场白、check-in 的 Q0 和 Q1、规则组 SY0、回忆开场三句和第一题、通通开场、想法练习对话页顶那一句。会话开始时写，算这个会话的第一行。
4. **存屏幕上显示的字。** 模型失败存后备句；回复被安全扫描拦下，不存模型原字；中度的安全句存；急性后的安全消息存成一段字：开头一句、危机页的机构名和号码（从同一份配置读）、「〔打開緊急求助頁〕」。
5. **不存的。** 每周回忆的大图和下面那一句（Junyu 说不用存；它不是老人或陪伴者的一句）；带按钮的卡片（想法练习邀请、转介卡、小篇章）；页顶的提示。卡片已在别处有记录（`turns` 的 `te`、`referral`，`reminiscence_chapters`）。check-in 的按钮代码照旧也在 `check_in_responses`。
6. **回忆 v2 隔天再进来**：等老人回答的那一题（连同它前面那几句）在新会话开头再存一次，`replyStatus: shown_again`，意思是「上次可能已存过」。这样每个会话单独拿出来也看得懂。
7. **什么时候写出。** 一行在老人下一句、会话结束、离开页面、App 退到后台时写出。老人打开页面一句没说就走：没有会话，开场白不存。
8. **规则**：新字段和取值都限死（`role` 只能两种；陪伴者行的老人字段必须为空、回复不能为空；`userInput` 只能三种或空）。冻结前的旧 App 仍写 schema 1，规则照旧接受。其他不变：只许本人新建、登记或测试员、开关开、原话 ≤ 5000 字、回复 ≤ 10000 字、任何客户端都不能读、改、删。
9. **不变的**：老人看到的东西；`turns` 行和所有埋点；规则组零 LLM（两层防线照旧）；安全检测（`lib/core/safety/`）；原文不发给任何模型。

## 考虑过的其他方案

| 方案 | 为什么没选 |
|---|---|
| 一个气泡一行 | 行数多一倍，读的人要自己把「老人说了什么、陪伴者回了什么」拼回来；Junyu 要的是每句老人话配陪伴者的回复 |
| 多加一个 `replyParts` 列表，一个气泡一项 | 规则没法限制列表里每一项的长度；同一段字存两份；导出成表格时一格看不完。用空一行分开已够分辨（固定问题、安全句都是已知的字） |
| 新开一个集合 | 删除脚本、盲法导出、规则都要再加一遍；同一个集合加 `role` 就够 |
| 每个气泡出现就写 | 规则只许新建、不许改，回复和下一题分两次写就拼不回同一行 |
| 只靠 `check_in_responses` 的按钮代码 | 读原文的人要两边对照；按钮文字直接进原文更清楚。`check_in_responses` 照旧 |

## 后果

- 对研究：冻结构建加规则部署之后，原文才完整。之前的 schema 1 旧行缺开场、固定问题、下一题和安全消息，按钮那一轮的老人原话是空的，补不回来。还没更新 App 的手机继续写 schema 1。读原文时按 `sessionId` 分组，按 `userSentAt`（陪伴者行用 `replyShownAt`）排序；`shown_again` 的行可去重。App 在前台时进程被杀，最后一行可能丢（退到后台前已写出）。
- 对开发：记录器多了「还没写完的一行」；各聊天页在显示气泡的地方加一行调用；规则、规则测试、Dart 测试、盲法检查、删除测试都改了。读取工具仍未做（见 backlog）。
- 对论文：方法部分写「研究期间保存每段对话里老人的每一句（含按的按钮）和陪伴者显示的每一句（不含图片）」，并和伦理批文、知情同意书核对。
