# 0003：分组由服务器分配，层内最小化

> 补记（2026-10-04）：这个决定当时在对话里做出，代码已合并。按模板补写，内容以当时的讨论为准。

- 日期：2026-09-30
- 状态：已被 0029 取代（2026-10-07：分组改为研究员登记后按 W0 DJG 情感分分层、置换区组；HTML 工具停用）
- 影响范围：phase_b × 两组
- 相关代码：PR #24（`functions/arm.js`、`assignArm`）

## 背景

原来的分组在手机上做：App 读计数器、自己决定组别，再写回 Firestore。规则只能限制写法，组别还是客户端算的，对 RCT 的可信度不够（`docs/research/arm_assignment_scheme_v1.md` 的 W1、W3、W6，D2）。

## 决定

注册后 App 调 Cloud Function `assignArm`，服务器在一个事务里分层（UCLA × 年龄，4 层）、按层内人数少的一组分配（一样多抛硬币）、写入组别和分配方式。重复调用不会重复计数。客户端不能写分组相关字段。

## 考虑过的其他方案

| 方案 | 为什么没选 |
|---|---|
| 继续在客户端分配 | 客户端理论上能影响组别 |
| 统计师预生成序列，研究员录入 | 当时没有选；如果研究上以独立的 HTML 随机化工具（v1.3.1）为准，需要改成这种做法，见 `docs/dev/memory-and-entry-spec.md` 第 1 节 |

## 后果

- 对研究：最小化方法要在 protocol 里预先声明；还没有每次分配的审计日志（W2）；`meta/arm_counter` 目前任何登录用户都能读（W1 的可预测性问题仍在）。
- 对开发：上线顺序必须是先部署函数、再发 App。
