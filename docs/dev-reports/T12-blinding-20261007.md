## 0. 结论

1. **新版盲法导出已写好，开关默认关**。打开后：每人一个跨周不变的研究编号，组别代码 Group_X/Y 整个研究期间固定，只导出两组都答的结局量表；对话轮次、会话、事件、LLM 和记忆相关集合**揭盲前一律不导出**。
2. **研究编号由服务器在分组时生成**，对照表放在 App 读不到的两个集合里，只有非盲角色（`role: pi`）能读。
3. **后台**：盲法人员（`role: researcher`）看不到两组人数，也看不到只有一组才有数据的板块。`meta/arm_counter`（各层两组人数）改为只有非盲角色能读。
4. **检查脚本** `tool/check_blinded_export.js`：对一份导出发现可疑字段就退出码 1。模拟器上生成的合成导出跑出 0；旧导出的样子跑出 1。

## 1. 开关

都在 `meta/blinding_config`（Firestore 规则：客户端不能读写，研究侧在控制台改）。

| 字段 | 默认 | 作用 |
|---|---|---|
| `enabled` | `false` | 开：分组时生成研究编号；每周导出改用新版，写到 Storage `exports_v2/{日期}/`。关：旧导出照旧（`exports/{日期}/`），不生成编号 |
| `includeBriefPr` | `false` | 新版导出是否带 `brief_pr`。两组弹出条件不同（决策 0015），每人的条数会暴露组别 |
| `includeUsageSummary` | `false` | 新版导出是否带 `usage_weekly`（每人每周会话数、活跃天数） |

代码：`functions/blinding.js` `configFromSnap`；`functions/index.js` `blindedDataExport` 开头。

## 2. 研究编号和对照表（给 T11 整人删除脚本）

- 形式：`P` + 6 位（Crockford base32，没有 I、L、O、U），随机，例如 `P7K3QX2`。`functions/blinding.js` `newResearchId`。
- 谁生成：服务器。`assignArm` 在同一个事务里生成（`functions/arm.js`，开关开时）；导出时遇到还没有编号的人，补发（`ensureResearchId`）。客户端不能写。
- 不写进 `users/{uid}`，App 读不到。

**对照表**（T11 的 `tool/delete_participant.js` 要一起删这两条）：

| 集合 / 文档 ID | 字段 | 读 | 写 |
|---|---|---|---|
| `research_id_map/{uid}` | `researchId`（string）、`createdAt`（时间）、`via`（`assign_arm` / `export_backfill`） | 只有 `role == 'pi'` | 只有服务器 |
| `research_ids/{researchId}` | `uid`（string）、`createdAt`、`via` | 只有 `role == 'pi'` | 只有服务器 |
| `export_blind_keys/stable_v2` | `mapping`（`{A: 'Group_X'或'Group_Y', B: …}`）、`createdAt` | 谁都不能（服务账号） | 只有服务器 |

删除一个人：删 `research_id_map/{uid}`，再按其中的 `researchId` 删 `research_ids/{researchId}`。`stable_v2` 是全体共用的，不删。已经导出的 `exports_v2/*` 文件里有这个人的研究编号，删除时也要处理（导出文件本来就在 T11 范围内）。

**跨周对得上**：研究编号存在对照表里，不随导出变；组别对应只生成一次。旧导出每周换盐、每周重抽 X/Y 的问题在新版里没有了（测试：`functions/test/blinding_emulator_test.js` “stable from week to week”）。

**新版仍然挡不住的（要研究侧知道）**：
- 结局分数本身的分布差异——这是要分析的东西，无法也不应去掉。
- `daily_mood` 两组都写，但签到 A、签到 B 各自也写，每人条数可能因组别略有不同（推断）。
- `weekly_pr.agentId` 由使用量最多的陪伴者决定，两组使用结构不同，分布可能偏（推断）。
- 开 `includeUsageSummary` 后，规则组“每次提交算一次会话”会让会话数偏高。
- 用户输入引起的安全事件数：Hybrid 组聊天轮次多，事件可能更多（推断）。

## 4. 研究者后台

- 角色用 Auth custom claims（`tool/provision_researcher.js` 发放）：`role: researcher` = 盲法；`role: pi` = 非盲；其他人拒绝。判断逻辑在 `lib/features/researcher_dashboard/data/dashboard_access.dart`。
- 盲法人员看到：未处理的 distress flags、参与者总数、Variant set、PPR 均分。
- 盲法人员**看不到**：Arm A / Arm B 人数；“對話審計隊列”（`agent_contexts` 只 A 有）；“想法練習審計”（含小欣的 AI 邀请文字）；“跨 agent 轉介”（只 A 有）。
- 以前只有 `researcher` 能进，`pi` 进不去；现在两个角色都能进，内容不同。
- **没有扩大读取权限**：规则仍不让研究员读别人的数据（T1 C19），后台本身仍没有入口，数据仍读不到。这次只做角色区分和隐藏。
- 这部分没有放开关：只对研究员可见、只减少显示内容。

## 5. 检查脚本

`node tool/check_blinded_export.js <导出文件夹>`。退出码：0 = 干净；1 = 有可疑项（逐条打印）；2 = 用法错误或没有文件。

查的内容：
- 文件名：不在白名单的、或属于“揭盲前不导出”的集合（含 `mem_*`）；
- 任何层级的字段名：`arm`、`uid`、`participantId`、`uidHash`、`llm`、`model`、`promptVersion`、`flags`、`source`、`source_surface`、`sessionRef`、`matchedTerm`、`freeResponse` 等（`DENY_KEYS`）；
- 字段值：`rule_based`、`deepseek`、`llm`、`users/...` 路径、28 位 uid 样式、16 位十六进制（旧 uidHash）；
- 每行必须有合规的 researchId；groupCode 只能是 Group_X / Group_Y；
- 超过 60 字的字符串（自由文字）。
