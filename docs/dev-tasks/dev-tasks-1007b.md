## T17 ADA 进 App（分支 `feat/ada`，SPEC:C22，只在 Phase A 配置下开启）

已定：先把 ADA（Agent Differentiation Assessment，三个 agent 的分辨问卷）做进 App，再推进 Phase A。结构以 Phase A 问卷 v1.3 附件 C 为准。研究侧会把定稿措辞放到 `docs/spec/instruments/ada.md`；在那之前，题目用下面的结构和占位文字。

1. 四个部分：
   - **A 使用频率**：三个 agent 各一行，4 档（完全冇 / 少过一次 / 一至两次 / 三次或以上）。题干里的回忆窗口可配置（v1.3 写“过去两个星期，正常一个礼拜”；Phase A 新版的窗口由研究侧给）。
   - **B 性格分辨**：4 个特质（温暖关心人、似自己同年纪、好奇鍾意问嘢、听我讲而唔评判我）× 3 个 agent，每格 1–5（完全唔似 · 少少 · 有啲 · 几似 · 好似）。
   - **C 功能分辨**：5 个情境（讲今日点过、讲旧时回忆、学新嘢、心情唔好、日常闲聊），每行单选：小欣 / 阿珍或阿伯 / 通通 / 边个都得。
   - **D 自由作答**：长文字，问三个 agent 有咩唔同、会同边个倾得多啲、点解。作答方式跟随语音输入开关：关着时只能打字，开了才显示麦克风。
2. **表单可配置，不要写死**：短版 = A+B+D，全版 = A+B+C+D。哪个时间点用哪一版、回忆窗口多长，都从配置读取（例如 `app_config/phaseA_schedule`）。Phase A 新版计划第 1 次到访当场一次、第 7 日一次，最终以 EA260417 的批复为准。
3. 阿珍 / 阿伯按参与者配对的性别显示。
4. 一屏一项（一个特质或一个情境一屏），可以返回上一屏，每屏保存。跳过规则先做成可配置，默认允许跳过并记录“跳过”。
5. **存储**：独立集合，例如 `ada_responses`。字段包括研究编号、表单版本（短/全）、时间点、每题原始值、开始和提交时间、D 部分的输入方式（打字/语音）。不要写进对话集合。
6. **安全**：D 部分的文字经过 T7 的统一安全检测入口。
7. **Phase B**：开关关闭，入口不可见。
8. 第 7 日的 3 道开放题复用 D 部分的长文字组件，题目先用占位文字，作答方式同样跟随语音开关。
9. 测试：在 emulator 上用合成数据各跑一次短版和全版；验证配置切换、性别配对、Phase B 构建里看不到入口、语音开关关闭时没有麦克风。

输出：PR 草稿，加上 `docs/dev-reports/T17-ada-YYYYMMDD.md`。报告附每一屏的截图、配置项说明和数据字段表。

## T18 W2 的 DJG 改为 App 内全 6 题（分支 `feat/djg-w2`，SPEC:C15，两组相同，只在 Phase B）

已定（10/7）：第 2 周的 DJG 只在 App 内做，不再面谈。社交分量表也要（H2' 要用），所以是全部 6 题。

1. **先报告现状**：App 里现有的 DJG（3 题、只做一次）在哪里触发、存在哪里、谁看得到、原本是哪个时间点用的。
   - 如果它就是 W2：用下面的 6 题版替换。
   - 如果它是别的用途（例如基线）：不要删，先报告给研究侧。
2. **触发**：从 W0 入组日起算第 14 天（香港时间，可配置），推送一次，并在首页显示问卷卡。开放窗口第 14–20 天（可配置）；24 小时没填提醒一次；过了窗口记为缺失，不再补推。
3. **题目和选项**：按已批问卷包 §3，照抄，不要改写。

   | 题号 | 分量表 | 题目（问卷包原文） |
   | --- | --- | --- |
   | 1 | 情感 | 我有一種空虛的感覺。 |
   | 2 | 情感 | 我想念身邊有人陪伴。 |
   | 3 | 情感 | 我經常覺得自己被人排斥。 |
   | 4 | 社交（反向） | 當我遇到問題時，有許多人可以倚靠。 |
   | 5 | 社交（反向） | 我有許多可以完全信任的人。 |
   | 6 | 社交（反向） | 有足夠多我感到親近的人。 |

   每题三个选项：是 / 大致是 / 不是。
4. **计分**（原始答案照存，分数另存）：
   - 第 1–3 题：答“是”或“大致是”记 1 分，“不是”记 0 分；加起来是情感分量表（0–3）。
   - 第 4–6 题反向：答“不是”或“大致是”记 1 分，“是”记 0 分；加起来是社交分量表（0–3）。
   - 总分 = 两个分量表相加（0–6）。
   - 有题被跳过时，对应分量表记为缺失，不要按 0 分算。
5. **作答**：一屏一题，可以返回上一题。允许跳过单题并记录“跳过”。两组的界面完全相同。
6. **存储**：独立集合，例如 `djg_responses`。字段：研究编号、时间点（W2）、每题原始值、两个分量表分、总分、推送时间、开始和提交时间、是否超出窗口。
7. **盲法**：W2 分数进入盲法导出，但不带任何能看出组别的字段。
8. Phase A 构建不显示。
9. 测试：
   - emulator 上用合成数据跑；
   - 时间边界：第 13、14、20、21 天；
   - 计分：至少覆盖全“是”、全“不是”、全“大致是”、单题跳过这几种情况，把预期分和实际分列成表。

输出：PR 草稿，加上 `docs/dev-reports/T18-djg-w2-YYYYMMDD.md`，附截图和计分测试表。

## T19 App 内分组重做（分支 `fix/randomization`，SPEC:C01）

已定（10/7）：
- 分组在 App 内完成。一个构建，两组共用；不再用 HTML 随机化工具，也不再用两个 APK。
- 分层变量：W0 纸本 DJG 的情感分量表分（0–3），由非盲研究员在注册时录入。0–1 分为低层，2–3 分为高层。不用老人自填的年龄组和 UCLA。
- 每层内 1:1 置换区组随机，区组大小 2 和 4 随机混用。

1. **先报告现状**：现在的分组算法是什么（随机，还是按计数器让两组人数相等）、分层变量从哪里来、计数器存在哪里、谁能写。
2. **入组登记**：做一个只有研究员账号能用的登记入口。可以是 App 里的研究员页面，也可以是管理脚本；选对研究员最省事、最不容易出错的一种，报告里写理由。录入内容：
   - 研究编号；
   - W0 情感分量表分（0–3 的整数，提交前要二次确认）；
   - 阿珍 / 阿伯的性别配对。
   老人自己的账号看不到这个入口。
3. **分配序列**：
   - 写一个脚本，用固定种子为两层各生成一条序列（每层至少 60 个位置）。每层内是 1:1 置换区组，区组大小 2 和 4 随机混用。
   - 序列上传到客户端完全不能读写的集合。
   - 生成和上传这一步由**非盲研究员**运行脚本完成，用他自己选的种子。PI 是盲法评估者，不能看到种子或序列。
   - 种子和序列文件导出一份，交导师离线保存。不要放进仓库。
   - 开启 Firestore 的数据访问审计日志，留下“谁读过分组和序列”的记录。PI 只用盲法导出和盲法视图。
4. **分配**：研究员提交登记后，由 Cloud Function 在事务里取该层下一个未用的位置，写入分组。同时写一条分配日志：研究编号、层、序列位置、时间、操作的研究员账号。
   - 一个研究编号只能分配一次。重复提交时返回原来的分组，不重新随机。
   - 分组写入后不能改。确需更正，只能用管理脚本，并且必须填写理由、留下日志。
   - 客户端不能写分组、计数器或序列。这一条修的是交接方案里的“分组计数器客户端仍能写”。
5. **揭示组别**：分配完成后，只在研究员的登记入口显示组别，供引导时按组讲解。PI 账号和后台的盲法视图看不到组别。
6. **两组隔离靠服务器保证**：规则组账号调用任何 LLM 生成接口都被拒绝，并记一条日志；只有 Hybrid 组才有的入口，在规则组不显示。报告里列出这些检查点各在哪里。
7. **测试**：在 emulator 上用 72 个合成参与者跑一遍，报告：
   - 每层两组各多少人、过程中最大的人数差；
   - 客户端读写序列、分组、计数器都被拒绝；
   - 重复提交不会重新分组；
   - 两个研究员同时提交，不会占用同一个序列位置；
   - 盲法视图看不到组别。
8. **上线配置**：`prelaunch_config.js` 加入上传序列和分层配置。上线检查清单补上三项：序列已上传、种子已离线保存、HTML 工具已停用。

输出：PR 草稿，加上 `docs/dev-reports/T19-randomization-YYYYMMDD.md`。

## T21 Phase A 与 Phase B 的配置分开（分支 `fix/phase-config-split`）

已定（10/7）：Phase A 和 Phase B 同期收数据，两期名单互斥。交接方案“已知风险”写着改 `app_config/phase_a` 会同时影响 Phase B 的人；同期进行时，这会让 Phase A 的调整改变 Phase B 的干预。

1. **先报告现状**：列出所有远程配置键（`app_config/*`、`meta/*`），每个标明 Phase A 用、Phase B 用还是两期共用；再写清构建开关（例如 `PHASE_B`）和远程配置各管什么。
2. **按研究期读配置**：每个参与者带一个研究期字段（A 或 B），登记时由研究员写入，客户端不能改。App 和 Cloud Functions 按这个字段读各自的配置（例如 `app_config/phase_a` 和 `app_config/phase_b`），不再共用一份。
3. **共用配置**：两期确实要一样的设置（例如安全检测、热线过滤）放进共用配置，报告里列出清单。以后改共用配置，要先经研究侧同意。
4. **Phase B 冻结**：首位 Phase B 参与者入组时，把 Phase B 配置导出存档，写进 `docs/STUDY_CHANGELOG.md`。之后每次改动都留日志：谁改的、什么时候、改了什么。
5. **数据分开**：对话、问卷、日志、`llm_calls`、记忆等每类数据都能按研究期筛出。盲法导出只含 Phase B。
6. **名单互斥**：同一个人不能同时进两期。先报告现在能用什么字段查重，并提出建议；不要为了查重新收集个人资料，也不要把查重用的个人资料写进日志或导出。
7. **测试**：在 emulator 上各建 5 个 Phase A 和 5 个 Phase B 合成参与者，验证：改 Phase A 配置后 Phase B 的行为不变；按研究期导出的数据正确；盲法导出里没有 Phase A 的数据。

输出：PR 草稿，加上 `docs/dev-reports/T21-phase-config-YYYYMMDD.md`。
