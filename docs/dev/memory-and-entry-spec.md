# 开发规格：记忆、分组与入口（Phase B 上线前）

> 决策日期：2026-10-01 ｜ 研究侧依据：`docs/research/memory-in-hybrid-arm.md` ｜ 决策记录：`docs/decisions/0001-*`
> 优先级：P0 = 冻结前必须完成；P1 = 来得及就做，来不及就不进 Phase B；P2 = 研究结束后再做
> 改动这里列出的任何行为，都要同步更新 `docs/STUDY_CHANGELOG.md`

## 0. 三条原则

1. **只有回应生成后端不同。** 两组的界面、导航、模块、推送时间完全一致。Hybrid 组的后端 = LLM 回复 + v1 记忆；规则组 = 脚本回复，没有记忆。
2. **冻结之后不改行为。** 上线后只修崩溃和安全问题，每次修复都要打新 tag 并记入 changelog（见第 6 节）。
3. **所有数据都能追溯到版本。** 每条消息都能查到当时用的代码、prompt、词表和模型版本。

## 1. 分组标记（P0，规则已同意）

- `users/{uid}.cohort` 取值为 `pilot`、`phase_a` 或 `phase_b`，由服务器的 `assignArm` 写入。Firestore 规则禁止客户端写这个字段。
- 一次性脚本：把所有现有账号标为 `pilot`。
- 注册时如果 `randomise` 关着，标 `phase_a`；开着就标 `phase_b`。
- 打开 `randomise` 之前，把 `meta/arm_counter` 清零。
- 分析和记忆相关的查询一律按 `cohort` 过滤，不再从 `armAssignmentMode` 推断。
- 删掉编译开关 `PHASE_B`，Phase A 和 Phase B 用同一个版本。

**阻断项，先确认再动手：** `assignArm` 和计数器的分组逻辑，与独立 HTML 随机化工具（v1.3.1，按 DJG-ES 分层）是什么关系？如果分组以 HTML 工具为准，`assignArm` 应该只负责写入研究员录入的分组结果，不应该自己按计数器去平衡。

## 2. 各 cohort 用哪套记忆

| cohort / 组别 | 记忆 | 备注 |
|---|---|---|
| `pilot` | v0（不变） | 不迁移 |
| `phase_a` | v1（待最终确认） | 和 Phase B 的 Hybrid 组体验保持一致 |
| `phase_b` Hybrid 组 | v1 | `meta/memory_config.policy = "C"`，研究期间锁定 |
| `phase_b` 规则组 | 无 | 不写缓冲区，也不注入记忆 |

## 3. P0：冻结前必须完成

### 3.1 记忆抽取测试集

- 位置：`tool/memory_eval/`，内容为 `dialogues/*.json`、`gold/*.json` 和 `run_eval.js`。
- 30 段合成粤语对话，每类至少 3 段：

| 类别 | 要验证什么 |
|---|---|
| 新事实 | 能否记到 |
| 更新已有事实 | 能否正确更新，而不是新增一条 |
| 纠正 | 能否识别出是纠正 |
| 相对日期 | 「下禮拜四」之类能否换算对 |
| 敏感内容 | 能否标为敏感 |
| 玩笑或假设句（「如果我中六合彩」） | 不应该记 |
| 陪伴者自己说的内容 | 不应该记 |
| 命中安全词 | 不应该记 |
| 「唔好記住」 | 不应该记 |

- 输出指标：召回率、捏造率（原话校验只保证原话存在，事实内容仍可能曲解原话，要人工核对）、更新错判率、纠正识别率、日期准确率、敏感误报率和漏报率。
- 每次改抽取 prompt 或换模型都要重跑。结果写进 `docs/validation/memory-eval-<日期>-<promptVersion>.md`。
- 验收：Junyu 审阅结果，并确认一次通过的版本号。

### 3.2 敏感话题词表 v1

- 沿用安全词库的 generator 做法：分类、扩展、完整性检查、统计词条数。
- 加一份误报测试句（笑死、死火、死慳死抵、錢包、唔啱聽之类），作为单元测试。
- 每条 `mem_facts` 都写入 `sensitivityLexiconVersion`。

### 3.3 口头删除（最小版）

- 意图词表：唔好記住、當我冇講過、忘記佢、唔好話俾人知等，附正反测试句。
- 触发后有三步：
  1. 该会话标 `doNotStore = true`，`memoryEndSession` 跳过抽取，直接清空缓冲区；
  2. 陪伴者当轮回复「好，呢樣嘢我唔會記住」，A 组由 prompt 规则实现；
  3. 如果老人指的是以前记住的事（「之前講嗰樣」），写一条 `mem_forget_requests`，在研究员 dashboard 显示，由研究员在 48 小时内手动处理。
- 规则组没有记忆，只做第 3 步的记录，以便研究员跟进。

### 3.4 分层摘要

- 保留每次会话一条的 `mem_summaries`。
- 新增 `mem_weekly`：`memorySweep` 每周一（香港时间）为每位用户把上周的会话摘要合成一条，不超过 200 字。
- 注入内容改为两部分：最近 3 天按天合并的行，加上全部周摘要（研究期内最多 8 条）。
- 整块封顶从 2,000 字放宽到 3,000 字，超出时的裁剪顺序不变。

### 3.5 每次会话只组装一次记忆块

- 会话开始时组装记忆块，写入 `sessions/{sessionId}.memoryBlock` 和 `memoryBlockHash`，之后每轮直接复用，不再每轮读 3 个集合。
- prompt 顺序：persona → 记忆块（整个会话不变）→ 对话历史 → 待跟进（只在第一轮，放在最后）。这样 DeepSeek 的前缀缓存能命中。

### 3.6 版本追溯字段

每条消息和每个 session 文档都写入：

| 字段 | 内容 |
|---|---|
| `buildSha` | 构建时注入的 git commit |
| `appVersion` | app 版本号 |
| `promptVersion` | 来自 prompt 注册表，见 3.10 |
| `memoryVersion` | `v0`、`v1.x` 或 `none` |
| `lexiconVersions` | `{distress, sensitivity, forget}` |
| `model` | DeepSeek 响应里返回的 `model` 字段，原样保存 |

### 3.7 「我的資料」页面（保持对等）

- 两组在同一位置（设置 → 我的資料）放同名入口。
- Hybrid 组页面内容：「我記得嘅嘢」列表（查看、确认、删除）+ 对话保留设定。
- 规则组页面内容：只有对话保留设定。
- 现有设置页里单独的「我記得嘅嘢」入口改为放在这个页面里面。

### 3.8 统一「会话」的定义

- 打开聊天页时生成 `sessionId`。会话在离开页面或 30 分钟无消息时结束。
- 下面四处都用这同一个 `sessionId`：
  - `proxyDeepSeek` 的每次调用；
  - `memoryEndSession` 和 `memorySweep`；
  - Brief PR 的作答记录；
  - 分析用的 session 表。
- **先确认现状：** Brief PR 现在是什么时候弹出的？如果和「离开聊天页」不是同一个时点，要先对齐。

### 3.9 回调实时匹配（只用于监测）

- Hybrid 组每轮回复生成后，检查回复里有没有出现本会话注入的事实或待跟进的关键词。
- 有就写一条 `mem_callbacks`：`{sessionId, turn, sourceType: fact|followup|summary, sourceId, matchedText}`。
- 只在 dashboard 上显示，论文的主要指标用人工编码。

### 3.10 Prompt 注册表

- 所有 persona、抽取和注入相关的 prompt 都放在 `functions/prompts/<name>.v<N>.txt`，不在代码里写字符串。
- 每个文件都有版本号，`promptVersion` 由正在使用的各文件版本拼成。

## 4. P1：来得及就做

### 4.1 入口整理（取决于现在的首页）

建议的结构如下，需要先对照现在的首页：

| 入口 | 陪伴者 | 承载的功能 |
|---|---|---|
| 每日推送 + 首页顶部卡片 | 小欣 | 签到、情绪快照、待跟进 |
| 陪伴者卡片 | 阿珍/阿伯 | 怀旧（每周一个主题）+ 自由倾偈 |
| 陪伴者卡片 | 通通 | 行动计划、社交建议（角色待确认） |
| 设置 → 我的資料 | — | 见 3.7 |

- 首页入口不超过 4 个，按陪伴者进入，不按功能进入。
- 推送时间和频率两组相同。Hybrid 组的开场白可以带待跟进，规则组用通用问候。
- 认知重构暂时不设独立入口，另行讨论。

### 4.2 微随机的预留开关（E4）

- 开关为 `meta/memory_config.mrtFollowupEnabled`，默认 `false`。
- 打开后，对每个有到期待跟进的会话按 p = 0.5 随机，结果写进 `mem_mrt`：`{sessionId, eligible, assigned, followupId}`。
- 注册和 HREC 修订批下来之前不得打开。

### 8.2 影响研究、需要负责人决定的

1. **DeepSeek 的模型版本可能在研究期间被悄悄换掉。** 请求的模型名不是固定日期的版本，DeepSeek 升级时同一个名字会直接指向新模型。2026-10-06 实测已经发生过一次：代码请求的 `deepseek-chat` 实际返回 `deepseek-flash`（DeepSeek-V4.1-Flash），请求已改为 `deepseek-flash` 并关闭思考（决策 0016）。返回的 `model` 字段能看出换了名字，但看不出同名之下换没换模型。能做的：同时记录响应里的 `system_fingerprint`（实测有返回，是否随升级变化还要观察），并在研究期间每周跑一次 3.1 的测试集，结果明显变化就当作 protocol deviation 记录。这是 fidelity 上最大的不确定性，建议写进局限。
2. ~~两组的 Brief PR 测量口径不同~~：已按决策 0015 处理（签到 B、回忆 B 每次提交后弹）。剩下的差别是触发门槛：聊天页 ≥2 句，表单页 1 次提交。
3. **规则组少了自由对话入口**（决策 0006），和第 0 节原则一冲突。
4. **3.5 改成每次会话只组装一次后，「注入次数」的定义会变**：现在 `mem_injections` 每轮记一条，改后每次会话一条。第 4 节的剂量统计要按新定义写。
5. **3.7「我的資料」在规则组几乎是空的。** 现在 App 里没有「对话保留设定」的界面（Phase A 改为纸本同意，`agent_onboarding_page.dart` 里写死为开）。规则组的页面里没有东西可放。要么新做这个设定（会改变同意流程），要么规则组页面只放一句说明。
6. **口头删除（3.3）「整次会话不存」会连带丢掉同一次会话里其他正常内容**，而且一次会话如果中途停了 30 分钟以上，`memorySweep` 已经把前半段整理掉了，后面再说「唔好記住」就管不到。可接受的话写进规格；不接受就要改成「删除最近 N 轮」。

### 8.3 技术上不确定、需要先试的

1. **抽取测试集（3.1）的「金标准」要人来写。** 30 段对话、每段的正确答案要由懂粤语的人标注，这是主要工作量，开发只能起草。「捏造率」要人工判断（原话在，但意思被曲解）；用另一个 LLM 自动判断可以省人工，但它本身的准确性又要验证。每次跑测试会真实调用 DeepSeek（30 段 × 1 次，费用很低），不放进 CI。
2. **敏感词表（3.2）**：现在是简单的「包含这个字就算」，`死` 会命中「笑死」，`醫` 会命中所有约诊。改成安全词库那样的分类 + 排除短语是可行的，但粤语口语的误报测试句要有人审。
3. **前缀缓存（3.5）**：DeepSeek 默认对重复的前缀做缓存，命中部分便宜很多，要求从开头逐字相同。persona + 记忆块整次会话不变，可以命中。不确定的是**待跟进「放在最后」**：放在对话历史后面需要在中间插一条 system 消息，DeepSeek 对这种格式的处理要实测；退路是把它接在最后一条用户消息里。另外，开场白（`greeting_*`）在会话开始前就生成，那时还没有 `sessionId`，需要另外处理。
4. **周摘要（3.4）规格没写清两点**：周摘要按陪伴者分开（和现在的共享策略 C 一致：摘要只给记下它的陪伴者），还是三个陪伴者合成一条？周摘要生成失败怎么办（重试几次、跳过那周）？封顶放宽到 3,000 字后，每轮 prompt 最多多约 2,200 tokens，成本可以接受。
5. **回调匹配（3.9）会很吵。** 事实是用繁体书面语存的（「孫仔叫明仔」），陪伴者用口语说（「你個孫明仔」）。只做关键词匹配会漏很多；用字的重合度会好一些，但仍然只能当参考，和规格「只用于监测」一致。
6. **`phase_a` 用 v1（第 2 节）** 需要把记忆的适用范围从「`armAssignmentMode == randomise`」改成按 `cohort` 判断，和第 1 节一起做。

### 8.4 规格里还缺的

- **分组审计日志**：第 1 节没写，但 `arm_assignment_scheme_v1.md` W2 建议无论哪种分组方式都要有。`meta/arm_counter` 现在任何登录用户都能读（W1），分组既然在服务器上做，应该关掉。
- **`buildSha` 怎么注入**：需要 CI 和 Codemagic 打包时传 `--dart-define=BUILD_SHA=…`；本地 `flutter run` 时没有，要有默认值（如 `dev`）。
- **工作量**：P0 十项加 cohort，开发约 8–12 天，不含测试集标注和词表审核的人工时间。比 0001 里估的 4–6 天多，主要多在 3.1、3.3、3.4、3.8。如果 Phase B 10 月中旬开始，建议先排：第 1 节、3.6、3.8、3.5、3.7，其余看时间。
