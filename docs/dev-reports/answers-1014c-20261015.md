## 第 3 题　对话传给 DeepSeek 前，代码去不去个人信息？去哪些？

**结论：去，但范围窄。** 服务器在每次出站到 DeepSeek 之前对文本跑 `stripPII`，用 4 条正则替换：香港电话（8 位，可带 +852）→ `[PHONE]`；邮箱 → `[EMAIL]`；香港身份证样式（1–2 个大写字母 + 6 位数字 + 可选括号校验位）→ `[ID]`；西式楼层/单位写法（`12F`、`3/F`、`5R`）→ `[ADDRESS]`。**不去姓名**（有意：生命回顾要用）、**不去中文地址**（「十二樓」「北河街」「3 座 12 樓 A 室」都不覆盖，所以 B08 写的"门牌"基本等于没去）、**不去银行账号**、不去中文数字电话。方法是正则，不是模型，有误伤（任意 8 位数字会被当电话）。

**证据**

- 规则本身：`functions/index.js` `PII_PATTERNS`（第 190–199 行）、`stripPII`（第 201 行）。注释写明姓名不剥离的理由。
- 用在哪里（三个 DeepSeek 入口 + 一个本地分类器）：
  - `proxyDeepSeek`（第 376 行起）：每条 `messages[]` 逐条 `stripPII`（第 445–448 行）；记忆块 `stripPII(memoryBlock)`（第 426 行）；`resolvePrompt` 里的 `contextSuffix`（滚动摘要、人名实体、心情片段）也过 `stripPII`（第 162 行）；请求头只有 `X-Session-Code`（uid 的盐哈希，`sessionCodeFor`），没有 uid、邮箱、IP。
  - `referralJudgement`（第 640 行起）：最近几轮和判断 prompt 都过 `stripPII`（第 704、707 行）。
  - 记忆抽取（`memoryEndSession` / `memorySweep`，第 1773–1784 行）：发给 DeepSeek 的用户内容 `stripPII(prompt.user)`。
  - 安全分类器（`functions/safety_classifier.js` 第 131 行）：送 LoRA 的文本也经 `deps.stripPII`（不是 DeepSeek，是自己的分类器）。
- **没过 `stripPII` 的出站**：`webSearch`（第 791 行起）把老人的搜索词 `query` 原样放进 Brave 搜索的 `q` 参数（第 817 行附近）——这是 Brave 不是 DeepSeek，开关 `webSearchEnabled` 默认关（决策 0019）。语音转文字（`functions/stt.js`）送的是音频到 Google Cloud Speech，不是文本，也不是 DeepSeek（T27）。
- 已有的范围说明：`docs/privacy/strip_pii.md`（P-2，2026-09），和现在的代码一致；里面已列"已知漏洞"：中文数字电话、中文地址、姓名、银行账号。
- Firestore 里存的 `turns`、`agent_contexts.rollingSummary`、`memory/*` 是**原文**，`stripPII` 只管出境，不管入库（`strip_pii.md` 第 1 节）。

**不确定的地方（如实说）**

- 滚动摘要是 DeepSeek 生成的；生成时输入已剥离，所以摘要里理论上不会再有电话、邮箱，但**会有人名**。
- 正则对粤语口语里夹的数字（例如「我住 12 樓」没有 F）不处理。

**研究侧要做什么（ICF 那句话）**

建议写成："对话内容在传给 AI 服务商（DeepSeek，服务器在中国内地）之前，系统会自动去掉电话号码、电邮地址、身份证号码和部分地址写法；**您在对话中提到的人名和其他内容会原样传送**。请避免在对话中说出银行账号等敏感号码。"——不要写"去掉门牌/地址"，因为中文地址实际不覆盖。如果 HREC 要求地址可控，要另开任务换方法（`strip_pii.md` 第 4 节建议 2）。

**结论：有，但时间字段是服务器收到的时间，不是老人手机上的时间。** `users/{uid}/events` 集合，`name` = `app_foreground` / `app_background`（还有 `session_start` / `session_end`、每次启动一条 `app_start` 带版本号）。事件里有 `arm`、`sessionId`、`locale`，**没有研究编号、没有构建版本（除 `app_start`）、没有"补传"标记**。未登录时只在内存里缓存，登录后补写。

**证据**

- 触发点：`lib/app/app.dart` `didChangeAppLifecycleState`（第 149–173 行）：`resumed` → `logSessionStart` + `logEvent(appForeground)`；`paused` / `detached` / `hidden` → `logEvent(appBackground)` + `logSessionEnd(exitReason: 'background')`；`inactive` 不记（系统弹窗）。进程启动 `initState`（第 93–110 行）：`logSessionStart` + `app_start`（带 `appVersion`、`buildNumber`、`lexiconVersion`、`promptBundleHash`、`platform`）。
- 事件名常量：`lib/core/session/chat_session_recorder.dart` 第 81 行 `appForeground = 'app_foreground'`。
- 写入：`lib/features/analytics/data/analytics_service.dart` `logEvent`（第 111 行）组装 `{name, params, sessionId, locale, highContrast, arm?, timestamp: 客户端 ISO 字符串}`；`_persist`（第 145 行）写 `users/{uid}/events`，**用 `'timestamp': FieldValue.serverTimestamp()` 覆盖了客户端的 `timestamp`**（第 158–161 行的展开写法，后者覆盖前者）。所以库里的 `timestamp` = 服务器写入时间；客户端时间**没有存下来**。handoff 第三节写的"客户端时间；没有服务器接收时间"**反了**，以本条为准。
- 未登录：`_uid == null` 时进 `_buffer`，`setUser` 后 flush（第 79–90 行）。登记前的老人（已登录、没 `cohort`）会照常写——登记门开时规则会拒绝 `users/{uid}/events` 的写入（T21 第 4.3 节），SDK 会把被拒的写丢掉。
- 研究编号：事件里是 uid；研究编号在 `research_id_map/{uid}`，导出时换。

**研究侧要做什么**

1. T40 收窄为"**补字段 + 开关**"，不新建集合：在 `events` 里补 `clientTs`（手机时间）、保留服务器 `timestamp`，`uploadedLate` 由两者差算；补 `buildNumber`（或在导出时用同进程最近一条 `app_start` 补）。登记前不记的问题由登记门规则兜住。
2. 这要**改 App，构建冻结前进包**（10/19 的 `phase_b_templates` 包）。如果来不及，退路是：导出时用 `app_start` 的版本和 `session_start` / `session_end` 的 `durationSeconds` 近似，前台/后台时间点只能用服务器时间。
3. 回访阶段的"使用天数"（T42 参加摘要）用 `sessions.isValid` 而不是 `app_foreground`，不受这里影响。

## 第 7 题　离线时事件怎么处理？会话日志是缓存后补传还是丢失？

**结论：缓存后补传，不会丢；但补传没有标记，而且时间会错。** App 没有改 Firestore 的离线设置（`lib/` 里没有 `persistenceEnabled` / `Settings(`），用 Flutter Firestore SDK 的默认：手机上离线持久化**开**，写入先落本地队列，联网后按顺序补传。会话、轮次、事件三类写入都是 fire-and-forget（不等服务器确认），断网时 UI 不卡。

**证据**

- 事件：`analytics_service.dart` `_persist` 第 147–152 行注释写明"Fire-and-forget ON PURPOSE：离线时 add() 要等服务器确认，await 会卡死 UI；SDK 本地排队、稍后同步"。
- 会话和轮次：`lib/core/session/chat_session_recorder.dart`——`sessions` 文档 `ref.set(...)`（第 496、579、623 行）、`turns` 文档 `turnRef.set(...)`（第 578 行）都包在 `unawaited(_guard(...))` 里；`_guard` 只吞错误打日志（不重试、不告警）。
- 时间字段：`sessions.startedAt` / `lastActivityAt` 是**客户端时间**（`Timestamp.fromDate(_startedAt!)`，第 504–505 行，`_clock = DateTime.now`）；`sessions.endedAt`（第 624 行）和 `turns.createdAt`（第 212 行）是 `FieldValue.serverTimestamp()`——补传时变成联网那一刻。`events.timestamp` 见第 6 题，也是服务器时间。
- 被规则拒绝的写入（例如登记门开着时没登记的人）SDK 会从队列里丢掉，不重试——这是预期行为（T21 第 4.3 节）。
- 没有测试覆盖离线路径（要真机断网）。

**所以**：一次离线聊天 → 联网后 `sessions`、`turns`、`events` 都会到；`sessions.startedAt` 是真实开始时间，`endedAt` / `turns.createdAt` / `events.timestamp` 是补传时间。单靠库里的字段**分不出**哪些是补传的，但可以用 `sessions.startedAt`（客户端）和 `endedAt`（服务器）之差过大来推断。

**研究侧要做什么**

1. T40 的 `uploadedLate` 做法：每条记录同时存客户端时间和服务器时间，差 > N 分钟算补传（N 建议 10 分钟，和会话超时一致）。`sessions` 已经有一半（`startedAt` 客户端），补 `endedAt` 的客户端版本即可；`turns`、`events` 要加 `clientTs`。
2. 老人手机没网时 LLM 不能用（Hybrid 会走本地回退 `llm_gateway.dart`），规则组不受影响；这不是日志的问题，但回访时要知道。
3. 分析计划里写明：会话时长用 `startedAt`（客户端）到 `lastActivityAt`（客户端）算，不用服务器 `endedAt`。
